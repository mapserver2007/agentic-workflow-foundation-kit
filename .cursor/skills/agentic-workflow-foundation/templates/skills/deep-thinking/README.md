# deep-thinking — ユースケースガイド

> SKILL.md（生成物）の補足ドキュメント。起動判断の実用ガイドラインを記載する。

## このスキルが解決する問題

単一エージェントによる回答は以下のバイアスを構造的に除去できない:

- **サイコファンシー**: ユーザー提案への過剰迎合
- **アンカリング**: 最初に検討した案への固着
- **確証バイアス**: 初期仮説を支持する証拠のみ収集
- **現状維持バイアス**: 変更コストの過大評価

A/B 並列分析 + C 統合裁定の構造により、これらのリスクを低減する（正確性・独立性・バイアス低減を保証するものではない）。

**ユーザーから見た体験は通常のチャットと同一**であり、内部の分析プロセスは表示されない。

## 動作の要点

- A（推進視点）と B（反証視点）は、同一の中立な分析ブリーフを受けて別プロセス・readonly で並列に分析する
- C（親エージェント）が A/B の証跡を統合し、結論を左右する主張は一次証跡で再確認して回答する
- 重要な矛盾が残る場合だけ、設定された上限まで匿名化した争点を再審する
- A/B の役割名・モデル名・分析過程・検証フラグは回答に表示しない

## 実行設定と前提

実行設定の SoT は [`config.yaml`](config.yaml) です。

- `models.analyst_a` / `models.analyst_b`: A/B に割り当てるモデル
- `execution.require_distinct_models`: A/B に異なるモデルを要求するか（静的 audit で検査）
- `execution.max_rounds`: round 0 を含む最大分析ラウンド数
- `execution.max_rebuttal_turns_per_issue`: 争点ごとの反駁上限
- `execution.max_issues_per_round`: 再審1ラウンドあたりの争点カード配布上限
- `execution.model_unavailable`: モデルが利用できない場合の方針
- `execution.stop_when`: 再審の停止条件
- `high_impact_categories`: リスクと不確実性を明示し、ユーザーの最終判断を必要とする領域

**静的検査**: config.yaml の構造・異モデル要求・再審予算・停止方針は基盤 audit（`bin/foundation-gate audit`）の静的ゲート G-DEEP-* で検査される。実行時のモデル実割当・A/B の相互非参照・別プロセス実行は Cursor Subagent API の制約により静的検査の対象外。

起動前に A/B の指定モデルが利用可能であることを確認する。利用不可時は同等モデルへ暗黙に代替せず、`config.yaml` の修正を促して終了する。A/B が同一モデルの場合、A/B の一致をモデル独立な検証とはみなさない（一次証跡の直接性を優先する）。

## 有効なユースケース

**共通特徴**: 「単一視点では見落としが生じやすい」かつ「回答の正確性・バランスが重要」

### 1. アーキテクチャ・設計判断の相談

- モノレポ vs ポリレポ
- サーバーレス vs コンテナ
- マイクロサービス分割の境界線
- DB 選定（RDB vs NoSQL、特定プロダクト選定）

一度決めると変更コストが高い判断について、反証を含めたバランスの取れた回答を得る。

### 2. トレードオフを含む技術的質問

- 「パフォーマンス最適化 vs コードの可読性」の境界線
- 「即時整合性 vs 結果整合性」の選択
- 「セキュリティ強化 vs ユーザー体験」のバランス点

正解がなく文脈依存の判断を含む質問に対して、多面的な分析に基づく回答を得る。

### 3. Go/No-Go の判断相談

- 大規模リファクタリングの投資判断（ROI が不明確）
- 技術的負債の返済優先度（今やるか・後にするか）
- 新技術の導入可否（実績不足 vs 将来性）

現状維持バイアスと新規性バイアスの両方が働く場面で、バランスの取れた回答を得る。

### 4. 複雑な問題の調査・分析

- 障害の根本原因分析で複数仮説がある場合
- パフォーマンスボトルネックの特定
- セキュリティリスクの評価

複数の仮説や視点を内部で並列検証し、統合された分析結果を得る。

### 5. 複数の実装アプローチが拮抗する設計判断

- 状態管理パターン（Redux vs Zustand vs Server State）
- 認証方式（Session vs JWT vs OAuth proxy）
- キャッシュ戦略（CDN vs Redis vs in-memory）

各候補が異なる軸で優位性を持ち、単純比較できない場面で活用する。

## 使うべきでない場面

| 場面 | 理由 |
| --- | --- |
| コードの diff レビュー | スコープ外（SKILL.md 明記） |
| 即答可能な質問 | コスト対効果が見合わない |
| PO が既に承認済みの方針 | 確定済みの再審は禁止 |
| 単純な実装手順の確認 | 多角分析の必要性が低い |
| 変数名・命名規約の選択 | 可逆性が高く、トレードオフが薄い |
| 小規模タスク（1-2ファイル） | コスト対効果が見合わない |

## 起動判断フロー

```
この質問は即答できるか？
  ├─ Yes → 通常のチャットで回答
  └─ No → 回答を間違えた場合の影響は大きいか？
              ├─ No → 通常のチャットで回答
              └─ Yes → 複数の合理的な見方があるか？
                         ├─ No（一つの見方で十分）→ 通常のチャットで回答
                         └─ Yes → deep-thinking を起動
```

**AND 条件**: 「即答不可」×「影響が大きい」×「複数の合理的な見方がある」

明示的に「多角的に考えて」「慎重に検討して」「deep-thinking で回答して」と依頼された場合も起動対象です。ただし、コード diff のレビューは `agent-code-review` の責務です。

## コスト認識

起動前にコンテキストバジェットへの影響を考慮する:

- A/B 並列起動 + C 裁定 + 最大 `max_rounds` ラウンド再審（`config.yaml` 参照）
- 評価完了後に実装フェーズのコンテキスト余裕が必要
- proxy 閾値の半分未満（prompt < 17, shell_bytes < 384KB）で完了する見込みがあるか事前確認

評価のみでセッションの Yellow（60%）に到達すると、実装品質が劣化する本末転倒が起きる。

## Plan Mode との関係

| ツール | 解決する問い | 出力 |
| --- | --- | --- |
| deep-thinking | **何をすべきか / どう考えるべきか** | 自然言語の回答（通常のチャット返答と同一体裁） |
| Plan Mode | **どう実装するか**（HOW） | プランファイル（.plan.md） |

両者は競合ではなく補完関係。典型的な併用パターン:

```
方針未確定 → deep-thinking（WHAT を決定）→ Plan Mode（HOW を計画）→ 実装
方針確定済み → Plan Mode（HOW を計画）→ 実装
```
