# multi-agent-evaluation — ユースケースガイド

> SKILL.md（生成物）の補足ドキュメント。起動判断の実用ガイドラインを記載する。

## このスキルが解決する問題

単一エージェントによる判断は以下のバイアスを構造的に除去できない:

- **サイコファンシー**: ユーザー提案への過剰迎合
- **アンカリング**: 最初に検討した案への固着
- **確証バイアス**: 初期仮説を支持する証拠のみ収集
- **現状維持バイアス**: 変更コストの過大評価

A/B 並列分析 + C 独立裁定の構造により、これらを低減する（保証ではない）。

## 有効なユースケース

**共通特徴**: 「判断を間違えた場合の手戻りコストが高い」かつ「どちらにも合理的な根拠がある」

### 1. アーキテクチャ選択（D-ARCH）

- モノレポ vs ポリレポ
- サーバーレス vs コンテナ
- マイクロサービス分割の境界線
- DB 選定（RDB vs NoSQL、特定プロダクト選定）

一度決めると全体の依存構造に波及し、後から変更するコストが非線形に増大する。

### 2. 外部 API・データモデルの破壊的変更判断（D-BOUNDARY）

- 既存 API のバージョニング戦略（breaking change vs 互換維持）
- スキーママイグレーション戦略（big bang vs 段階的）
- 外部連携先とのインターフェース設計

`config.yaml > high_impact_categories` の `breaking_external_api` / `data_deletion_or_migration` に直接該当。

### 3. 方針未確定の要件トレードオフ（D-WORKFLOW）

- 「パフォーマンス最適化 vs コードの可読性」の境界線
- 「即時整合性 vs 結果整合性」の選択
- 「セキュリティ強化 vs ユーザー体験」のバランス点

正解がなく、文脈依存の価値判断を含む。単一エージェントはユーザー提案に迎合しやすい。

### 4. Go/No-Go 判断

- 大規模リファクタリングの投資判断（ROI が不明確）
- 技術的負債の返済優先度（今やるか・後にするか）
- 新技術の導入可否（実績不足 vs 将来性）

現状維持バイアスと新規性バイアスの両方が働く場面で、反証構造が機能する。

### 5. 複数の実装アプローチが拮抗する設計判断（D-PATTERN）

- 状態管理パターン（Redux vs Zustand vs Server State）
- 認証方式（Session vs JWT vs OAuth proxy）
- キャッシュ戦略（CDN vs Redis vs in-memory）

各候補が異なる軸で優位性を持ち、単純比較できない。

## 使うべきでない場面

| 場面 | 理由 |
| --- | --- |
| コードの diff レビュー | スコープ外（SKILL.md 明記） |
| 変数名・命名規約の選択 | 可逆性が高く、トレードオフが薄い |
| PO が既に承認済みの方針 | 確定済みの再審は禁止 |
| 実装手順の組み立て | HOW の問題であり WHAT ではない |
| 小規模タスク（1-2ファイル） | コスト対効果が見合わない |
| 一方が明らかに Must 違反 | 単純な消去法で決まる |

## 起動判断フロー

```
この判断は不可逆か？（戻すコスト > 実装コスト）
  ├─ No → 直接判断して試す
  └─ Yes → 実行可能な候補が2つ以上あるか？
              ├─ No（1択）→ 直接実行
              └─ Yes → トレードオフは自明か？
                         ├─ Yes → 直接判断
                         └─ No → multi-agent-evaluation を起動
```

**AND 条件**: 「不可逆」×「非自明なトレードオフ」×「複数候補あり」

## コスト認識

起動前にコンテキストバジェットへの影響を考慮する:

- A/B 並列起動 + C 裁定 + 最大 `max_rounds` ラウンド再審（`config.yaml` 参照）
- 評価完了後に実装フェーズのコンテキスト余裕が必要
- proxy 閾値の半分未満（prompt < 17, shell_bytes < 384KB）で完了する見込みがあるか事前確認

評価のみでセッションの Yellow（60%）に到達すると、実装品質が劣化する本末転倒が起きる。

## Plan Mode との関係

| ツール | 解決する問い | 出力 |
| --- | --- | --- |
| multi-agent-evaluation | **何をすべきか**（WHAT） | 判断レポート（チャット出力） |
| Plan Mode | **どう実装するか**（HOW） | プランファイル（.plan.md） |

両者は競合ではなく補完関係。典型的な併用パターン:

```
方針未確定 → multi-agent-evaluation（WHAT を決定）→ Plan Mode（HOW を計画）→ 実装
方針確定済み → Plan Mode（HOW を計画）→ 実装
```
