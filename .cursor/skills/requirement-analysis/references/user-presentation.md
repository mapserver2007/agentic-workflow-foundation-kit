# ユーザー向け提示テンプレ集

> requirement-analysis スキルの「ユーザーへの質問・報告・進捗サマリ」を組み立てる際に参照する文面集。内部の機械契約（YAML キー・enum 値・envelope スキーマ）は維持したまま、ユーザーに見える文面を人間向けラベルに統一する。

---

## 用語対応表

| 内部語（機械契約で残す） | ユーザー向け表示 |
| --- | --- |
| Gate A / `requirement_gate` | 要求の完全性チェック |
| Gate B / `spec_consistency_gate` | 仕様との整合性チェック |
| Gate C / `feasibility_gate` | 実現可能性チェック |
| Issue Ledger | 確認事項一覧 |
| `blocking: true` | 先に解決が必要 |
| `blocking: false` / non-blocking | 後で決めてよい警告 |
| `INCOMPLETE` | 不足あり（追加情報が必要） |
| `PASS` | 通過 |
| `standard` / `deep` / `deferred` | 標準分析 / 深い分析 / 調査後に再判定 |
| Investigation Memo | 調査メモ |

**ルール**: ユーザー向け文面では内部語を単独ラベルとして出さない。必要な場合のみ人間向けラベルの後に括弧で内部識別子を補足する（例: `要求の完全性チェック（内部: Gate A）`）。

## 不足時の質問テンプレ（ガード失敗時）

### 要求の完全性チェック（Gate A）で不足がある場合

```
**要求の完全性チェック**で、次の情報が不足しています（先に解決が必要）。

1. **確認事項（RA-{NNN}）** {不足項目の人間向け説明} — {なぜ必要かの1行説明}
2. **確認事項（RA-{NNN}）** {不足項目の人間向け説明} — {なぜ必要かの1行説明}

回答いただければ、同じチェックを再実行して進めます。
```

### 仕様との整合性チェック（Gate B）で矛盾がある場合

```
**仕様との整合性チェック**で、既存の仕様ドキュメントとの矛盾が見つかりました（先に解決が必要）。

1. **確認事項（RA-{NNN}）** {矛盾の内容} — {どの仕様文書と矛盾しているか}
2. **確認事項（RA-{NNN}）** {矛盾の内容} — {どの仕様文書と矛盾しているか}

どちらの記述を正とするか教えてください。確認後、チェックを再実行します。
```

### 実現可能性チェック（Gate C）で問題がある場合

```
**実現可能性チェック**で、実装上の課題が見つかりました（先に解決が必要）。

1. **確認事項（RA-{NNN}）** {課題の内容} — {影響範囲と判断に必要な情報}

方針を教えてください。確認後、分析を続行します。
```

## 進捗サマリテンプレ

### チェック通過報告

```
**要求分析の進捗**:

- 要求の完全性チェック: ✅ 通過
- 仕様との整合性チェック: ✅ 通過
- 分析深度: {標準分析 / 深い分析}（{判定理由を1行}）
- 実現可能性チェック: ✅ 通過

確認事項はすべて解消済みです。Step ② レポート作成に進みます。
```

### 全チェック通過 + non-blocking 警告あり

```
**要求分析の進捗**:

- 要求の完全性チェック: ✅ 通過
- 仕様との整合性チェック: ✅ 通過
- 分析深度: {標準分析 / 深い分析}（{判定理由を1行}）
- 実現可能性チェック: ✅ 通過

以下の警告が残っていますが、後工程で対応可能なため続行します（後回し可能）。

- {警告内容}

Step ② レポート作成に進みます。
```

## 例外経路テンプレ

### 再試行上限到達時（`gate_retry_exceeded`）

```
**{該当チェック名}** を {N} 回実施しましたが、以下の確認事項が解消できませんでした。

未解消の確認事項（先に解決が必要）:
1. {issue の人間向け説明}

このまま続行するには追加の情報が必要です。
追加情報を提供いただくか、リスクを承認して続行するかを教えてください。
```

### 外部依存で解決不能時（`blocked_external`）

```
以下の確認事項は外部の回答待ちのため、現時点では先に進めません。

外部回答待ち:
1. {issue の人間向け説明} — 待ち先: {外部依存先}、解除条件: {待ち条件}

外部の回答が得られた時点でお知らせください。分析を再開します。
```

### deep-thinking 無効時の警告

```
このタスクは**深い分析**が推奨されますが、deep-thinking が無効のため**標準分析**で続行します。

推奨理由: {deep 判定された理由を1行}

より深い分析が必要な場合は、deep-thinking を有効にして再実行してください。
```

### deep 起動失敗時のユーザー確認

```
**深い分析**を実行しようとしましたが、モデルが利用できませんでした。

以下のいずれかを選択してください:
1. **標準分析で続行** — 分析の深さは限定されますが、作業を進められます
2. **中断** — モデルが利用可能になってから再開します
```

### Step① 退出不合格時の状況報告

```
**調査・分析の退出チェック**で、以下の項目がまだ満たされていません。

未通過の項目:
- {未通過項目: 実現性 / 影響範囲の明確化 / 実装方針の特定 / 実装アプローチの立案 / 優先度の決定}

現在の調査状況:
- {調査で判明していること}

不明な点:
- {特定できていない項目}

先に解決が必要な確認事項:
- {blocking issue の人間向け説明}

追加で必要な情報:
- {ユーザーに確認してほしいこと}
```

## 確認事項の表示分類

Issue Ledger の内部構造をユーザーには以下の 4 分類で表示する。

| 表示分類 | 内部状態 | ユーザーの次のアクション |
| --- | --- | --- |
| **先に回答が必要** | `blocking: true` + `status: open` + `resolution_owner: user` | 回答を求める質問を提示 |
| **後回し可能** | `blocking: false` + `status: open` | 情報提供として通知。回答は任意 |
| **外部回答待ち** | `status: blocked_external` | 外部回答が得られたら連絡を依頼 |
| **解決済み** | `status: resolved` / `status: waived` | 必要な場合だけ解消内容・根拠を表示 |

### 確認事項の提示テンプレ

```
**確認事項一覧**

先に回答が必要:
1. {summary} — {impact の人間向け説明}
2. {summary} — {impact の人間向け説明}

後回し可能:
- {summary}（後工程で確定可能）

外部回答待ち:
- {summary} — 待ち先: {resolution_owner の具体名}

解決済み（{N}件）:
- {summary}: {resolution の要約}
```

「先に回答が必要」が 0 件の場合はそのカテゴリを非表示にする。同様に、各カテゴリが空の場合は省略してよい。

## 禁止事項

ユーザー向け文面で以下の内部語を**単独ラベル**として使ってはならない。

| 禁止（単独使用） | 許容（括弧内の補足として） |
| --- | --- |
| `Gate A` | 要求の完全性チェック（内部: Gate A） |
| `Gate B` | 仕様との整合性チェック（内部: Gate B） |
| `Gate C` | 実現可能性チェック（内部: Gate C） |
| `Issue Ledger` | 確認事項一覧 |
| `INCOMPLETE` | 不足あり |
| `blocking` | 先に解決が必要 / 後回し可能 |
| `envelope` | （ユーザー向け文面では言及しない） |

## 質問時の ID 付与と差分提示

### RA-ID 付き質問テンプレ

```
**確認事項**（RA-{NNN}）

{質問内容} — {なぜ必要かの1行説明}
```

質問には必ず `RA-xxx`（3桁ゼロ埋め）を付与する。ユーザー回答を受けて Issue Ledger の該当 `RA-xxx` を `resolved` に遷移し、`resolved_evidence` に回答要約を記録する。

### 要件差分の提示テンプレ

回答により要件が変更された場合、差分をユーザーに明示する:

```
**要件の更新**（RA-{NNN} の回答を反映）

変更前:
- {変更前の要件記述}

変更後:
- {変更後の要件記述}

この変更でよろしいですか？
```

### 要件確定の進捗通知テンプレ

Step① 機械退出前の4分類サマリ提示:

```
**要件分析の完了**

確定事項:
- {確定済み要件の要約}

AI提案（要確認済）:
- {AI が提案しユーザーが確認済みの事項}

未決定（後工程で対応可能）:
- {non-blocking の未確定事項}

外部回答待ち:
- {該当する場合}

受入条件:
- AC-001: {条件}
- AC-002: {条件}

要件と受入条件を `requirements_digest` に固定し、Step①の機械検査後、同一ターンで Step② レポート作成を開始します。

実装開始の承認は、機械検査済みの完成レポートを確認した後の PO `implementation_approval` だけで判断します。
```
