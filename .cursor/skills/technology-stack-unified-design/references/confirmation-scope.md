# `[要確認]` の採否

設計書が渡す相手は [`workflow-orchestrator`](../../workflow-orchestrator/SKILL.md) の Step ①〜⑥ である。デプロイ、GitHub Actions の成否、保護ブランチの必須 check は、このスキルの外で行う。未確定でも、そのステップの手順を分岐させないものは `[要確認]` にしない。

validator はこの採否を検査しない。起草と自己レビューで適用する。

## 残す

次をすべて満たすときだけ `[要確認]` にする。上限を超える分は §24 に優先度の高い順で置く。

1. 開いたファイルからは、ステップが行う手順が一つに決まらない。
2. 観測または推定として書くと、実装・調査・ローカル検証が互いに相容れない選択肢へ分かれる。
3. その分岐は Step ①〜⑥ のどれかの入口である。

| Step | 設計書が渡す要素 | `[要確認]` にする例 |
| --- | --- | --- |
| ① 調査 | 契約の正本、層、既存パターン、実現可能性 | 新しい API の認可をどの実装に置くか、併存したまま一つに決まらない |
| ② レポート | ①の結論を実装方針として一文にできること | ①で分岐したまま、レポートの実装方針が一つに書けない |
| ③ 実装 | 踏襲するパターン、層の境界、エラーの置き場、契約変更からテストまでの順序 | 新規コードが従う正本が複数残っている |
| ④ テスト | テストの種別と、プロファイルのコードゲート（G-BUILD / G-LINT / G-TEST / G-GEN）のローカルな入口 | ローカルでどのコマンドを通すかがファイルから決まらない |
| ⑤ PR | PR 作成とレビュー指摘の検証に必要な契約・規約 | レビュー手順そのものは orchestrator 側にある。設計書の `[要確認]` には通常しない |
| ⑥ 完了 | Domain docs へ反映する境界（API、schema、アーキテクチャ） | 反映先の正本がリポジトリ内で複数あり、起票先が分かれる |

新規コードの規則がコメント、ルール、または既存の主流から既に読めるときは、残件の期限や廃止日を `[要確認]` にしない。規則を本文の手順として書く。

## 除外する

次はトークン `[要確認]` を付けず、§24 にも並べない。事実がステップの観測として必要なら、該当節に観測文で書く。

- デプロイ先、クラスタ、イメージの昇格、リリースチャネル
- GitHub Actions の job 成否、matrix の未使用分岐、branch protection の必須 check
- ステップが実行するコマンドが既に一つあるときの、CI や本番との pin の突き合わせ（例: ローカルの `make db-migrate` は決まっているが、運用イメージのタグと揃えるかは未決）
- 新規コードの規則が既にあるときの、移行完了条件と廃止日
- 既存の欠陥を直すか残すかの採否。新規コードがしてはならないことは、観測された禁止として書く
- リポジトリ外の過去 ADR の理由文。新しい D-* の記録は orchestrator が `docs/DECISIONS.md` へ行う

§9 の方針列は、ステップが使う単一の pin があるときだけ `宣言:` とする。上の除外に当たり、単一の pin がステップの入力でないときは `—` とし、観測した pin の併存は備考の `観測:` に書く。pin の矛盾を理由に `[要確認]` へしない。

## 自己レビューでユーザーへ出すもの

`[要確認]` の各項目に、止める Step 番号を一文で添える。除外した未確定は種別（デプロイ、CI の成否、必須 check、pin の突き合わせ、廃止日、既存欠陥の採否、リポジトリ外の理由文）で短く列挙する。本文には書かない。
