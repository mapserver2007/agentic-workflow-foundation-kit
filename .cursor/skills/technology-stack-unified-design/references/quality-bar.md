# B 水準の品質基準

reverse-draft が「使える統一設計書」であるための品質の定義。見本は kit 正本 `.cursor/docs/TECHNOLOGY_STACK_UNIFIED_DESIGN.md`（以下 B）。**固定するのは構造・密度・書き方であり、B の技術（Cloudflare 等）や章題はコピーしない。** B が持つ Appendix は、本スキルの出力では生成しない。

## 1. 定義

B 水準とは、文脈を知らない読み手がこの 1 本だけで次を判断できる状態をいう。

- この実装は **何を契約の正本とし、どの層がどの責務を持ち、何を禁じているか**（設計）
- **どの技術を、どのバージョン方針で、どの経路（ローカル → CI → デプロイ）で使っているか**（スタック）
- **何を割り切り、何を代替として採らなかったか、どこが未確定か**（意思決定）

証跡ログ（観測した事実の列挙）は B 水準ではない。**観測した事実を、設計の構造として組み上げたもの**が B 水準である。

## 2. 低品質（A）の症状と是正

| 症状 | なぜ使えないか | 是正 |
| --- | --- | --- |
| 1 節が密な 1 段落、または `evidence:` の羅列 | 読み物でなく証跡ログ。備考に残ると kit の note に入る | 本文は主張と構造で書く。`evidence:` トークンは置かない |
| 各節末尾に `[要確認]` が必ずある | 読み手が判断できない。調査の手抜きの隠れ蓑になる | 実装から導ける設計は **推定として書く**。[`confirmation-scope.md`](confirmation-scope.md) に残すものだけを `[要確認]` にし、上限を超える分は §24 に優先度の高い順で集約する。デプロイや CI の成否は除外する |
| 「代表ファイルしか読んでいない」と本文で免責する | 全量読解の仕組みが無かった結果 | survey + shard 読解で全可読ファイルの読解台帳（note）を完成させ、`調査範囲:` 行で到達範囲を示す |
| 表・図・ツリー・フローが無い | 構造を一目で把握できない | §5 原則表 / §6 構成図 / §7 ツリー / §8 責務表 / §16 フローなど B の構造要素を置く |
| 技術一覧が事実の羅列で、役割と選定理由が無い | 「なぜそれか」「何と何が連携するか」が分からない | §9 の表に加え §3・§4・§22 で採否・整合・割り切りを論じる |
| 数値・名前が実装と食い違う（幻覚） | 設計書への信頼が崩れる | 数値・名前は書く前に対象行を開いて確かめる。本文へ `evidence:` は書かない |

## 3. B 水準の 9 要件

1. **設計として書く**: 「〜とする」「〜してはならない」「〜を正本とする」の規範文で、実装が従っている規約を明文化する。実装から言える範囲に限り、観測した事実として書く。`evidence:` は置かない。
2. **1 節 = 主張 + 構造要素**: 各節に、主張（段落）と、構造要素（表・図・ツリー・フロー・箇条書き）を置く。根拠トークンは付けない。
3. **構成図とツリーを置く**: §6 は ASCII の構成図（fenced code）とデプロイ単位表、§7 は役割コメント付きのディレクトリツリー（fenced code）。
4. **責務表で境界を明文化する**: §8 は「層 / パッケージ / 責務 / やってはいけないこと」の表。依存の向きは import 集計（survey の `層間 import 集計`）で裏取りし、逸脱は件数と代表例を書く。
5. **原則表**: §5 は「原則 / 要約 / 参照節」の表。反復して現れる制約・規約を、観測件数と代表例を根拠に原則化する。
6. **採否とトレードオフを正直に書く**: 採用した選択、実装から観測できる代替の痕跡（併存する 2 系統・移行途中・非対称）を §3 の表に、割り切りを §22 に書く。**良し悪しを断定せず条件付きで評価する**。
7. **ナビゲーション**: 本文は他節を `§N` で相互参照する。大きな論点（§21 等）は `####` 小見出しで「方針 → 責務分離 → 論点の確定表 → 経路 → 将来」と分ける。
8. **事実・推定・未確定を書き分ける**（§5 参照）。残す未確定だけを §24 に優先度の高い順で集約する。採否は [`confirmation-scope.md`](confirmation-scope.md)。
9. **文脈のない読み手に通じる**: 固有の略語・内部名・生成器名は初出で説明する。「前述のとおり」ではなく節番号で参照する。

## 4. 機械検査される床

`validate_design_doc.py` は次を検査する。これは**最低線**であり、B 水準はこれを大きく上回る。検査しない項目（意味の正しさ）はユーザーレビューで確認する。

### 4.1 文書全体（standard プロファイル）

| 項目 | 床 |
| --- | --- |
| 本文の分量（§1〜§24、空白除く） | 18000 文字以上 |
| `evidence:` トークン | 0。本文・表・備考・fenced code のいずれにも書かない |
| 本文の `[要確認]` | 1 節 2 件まで、§9 と §24 を除く本文で合計 14 件まで。上限を超える未確定事項は §24 へ集約する |
| `該当なし:` | 4 節まで。根拠は 20 文字以上で、探した対象を具体的に書く |
| §9 方針列の `[要確認]` | 行数の 25% 以下 |
| Appendix・証跡台帳 | `## Appendix` / `### Appendix` 見出し、目次の Appendix リンク、`[E<n>]` 参照を置かない |
| 調査範囲 | survey が算出した `調査範囲:` 行を導入部へ逐語で置く |

### 4.3 compact プロファイル

読解対象の可読ファイルが 60 件未満の小規模リポジトリでは自動で `compact`（文字数の床を約 40%）になる。`--profile standard|compact` で明示もできる。小規模でも**構造（表・図・調査範囲行）は省略しない**。`evidence:` はどちらのプロファイルでも書かない。

## 5. 事実・推定・未確定の書き分け

| 区分 | 書き方 | 調査 |
| --- | --- | --- |
| 観測 | 断定で書く。数値・名前・パスは対象行と一致させる | 対象行を開いて確かめる。本文にトークンは残さない |
| 推定 | 「〜と読み取れる」「〜を原則としている（N 件中 M 件で一致）」と書く。**件数・代表例・例外**を添える | 代表パスを本文の言葉で書く |
| 採用理由 | README・ADR・コメント等に書かれているものだけを理由として書く。無ければ「意図は文書化されていない」と書き、推定の理由を「推定:」と明示する | 文書に理由が無いときは推定と分ける |
| 未確定 | Step ①〜⑥ の手順が一つに決まらないものだけを `[要確認]` にする（[`confirmation-scope.md`](confirmation-scope.md)）。1 節 2 件まで。残りは §24 に優先度の高い順で集約する。デプロイ、CI の成否、必須 check、pin の突き合わせ、廃止日、既存欠陥の採否、リポジトリ外の理由文はトークンにしない | 残す理由と、止める Step 番号を 1 文で |

観測と推定を混ぜない。**推定を観測として書くことが最大の不誠実**である。validator は `evidence:` の混入を拒否する。引用行と主張の一致は検査しない。レビューでは断定で書かれた数値・名前を対象ファイルと突き合わせて抜き取り確認する。

## 6. 根拠トークンは書かない

設計書のどこにも `evidence:` を置かない。§9 の備考は foundation の ingest が `tech_stack.items.note` へそのまま写す。根拠リンクは kit の入力ではなく、Domain 層の技術一覧に残ると読み手の障害になる。

- 数値・version・名前・環境変数名・ポート・テーブル名は、対象行を**ファイルを開いて**確かめてから、観測文として書く。
- survey の `facts/*.md` は `path#L行 | 逐語テキスト` 形式の調査メモである。設計書へその形式をコピーしない。
- ファイル名を本文で挙げるのはよい。`evidence:` という印と行番号トークンは付けない。

## 7. 提出前の自己レビュー（Selective）

1. 各節を「この節だけを読む人は、何が決まっているか分かるか」で読み直したか。
2. 各 §N の主張は、構造要素（表・図・フロー）で示せているか。段落だけの節は無いか。
3. 数値・名前を対象行で確かめたか。推定を観測として書いていないか。本文に `evidence:` が残っていないか。
4. `[要確認]` を節末の保険に使っていないか。各項目は Step ①〜⑥ のどれを止めるか。除外対象が §24 に残っていないか。残したもののうち上限を超える分は §24 に優先度の高い順であるか。
5. §3・§22 に、観測できる代替・併存・割り切り（例: 2 系統の生成器、版の食い違い、移行途中）が書かれているか。
6. 層間 import 集計の逆方向・循環を §8 と §22 に反映したか。
7. `validate_design_doc.py` が PASS し、`調査範囲:` 行が導入部にあるか。
