# B 水準の品質基準

reverse-draft が「使える統一設計書」であるための品質の定義。見本は kit 正本 `.cursor/docs/TECHNOLOGY_STACK_UNIFIED_DESIGN.md`（以下 B）。**固定するのは構造・密度・書き方であり、B の技術（Cloudflare 等）や章題はコピーしない。**

## 1. 定義

B 水準とは、文脈を知らない読み手がこの 1 本だけで次を判断できる状態をいう。

- この実装は **何を契約の正本とし、どの層がどの責務を持ち、何を禁じているか**（設計）
- **どの技術を、どのバージョン方針で、どの経路（ローカル → CI → デプロイ）で使っているか**（スタック）
- **何を割り切り、何を代替として採らなかったか、どこが未確定か**（意思決定）

証跡ログ（観測した事実の列挙）は B 水準ではない。**観測した事実を、設計の構造として組み上げたもの**が B 水準である。

## 2. 低品質（A）の症状と是正

| 症状 | なぜ使えないか | 是正 |
| --- | --- | --- |
| 1 節が密な 1 段落 + `evidence:` 行の羅列 | 読み物でなく台帳。設計の構造が見えない | 本文は主張・構造・理由を書き、根拠は `[E<n>]` で Appendix B 台帳へ集約する |
| 各節末尾に `[要確認]` が必ずある | 読み手が判断できない。調査の手抜きの隠れ蓑になる | 実装から導ける設計は **推定として書く**。本当に未確定のものだけを Appendix E へ優先度付きで集約する |
| 「代表ファイルしか読んでいない」と本文で免責する | 全量読解の仕組みが無かった結果 | survey + shard 読解で全可読ファイルを台帳化し、`調査範囲:` 行で到達範囲を示す |
| 表・図・ツリー・フローが無い | 構造を一目で把握できない | §5 原則表 / §6 構成図 / §7 ツリー / §8 責務表 / §16 フローなど B の構造要素を置く |
| 技術一覧が事実の羅列で、役割と選定理由が無い | 「なぜそれか」「何と何が連携するか」が分からない | §9 の表に加え §3・§4・§22・Appendix A で採否・整合・割り切りを論じる |
| 数値・名前が実装と食い違う（幻覚） | 設計書への信頼が崩れる | 台帳引用の逐語実在を validator が検査する。数値は台帳で裏取りする |

## 3. B 水準の 10 要件

1. **設計として書く**: 「〜とする」「〜してはならない」「〜を正本とする」の規範文で、実装が従っている規約を明文化する。実装から言える範囲に限り、根拠を `[E<n>]` で示す。
2. **1 節 = 主張 + 構造要素 + 根拠**: 各節に、主張（段落）と、構造要素（表・図・ツリー・フロー・箇条書き）と、根拠参照を置く。
3. **構成図とツリーを置く**: §6 は ASCII の構成図（fenced code）とデプロイ単位表、§7 は役割コメント付きのディレクトリツリー（fenced code）。
4. **責務表で境界を明文化する**: §8 は「層 / パッケージ / 責務 / やってはいけないこと」の表。依存の向きは import 集計（survey の `層間 import 集計`）で裏取りし、逸脱は件数と代表例を書く。
5. **原則表**: §5 は「原則 / 要約 / 参照節」の表。反復して現れる制約・規約を、観測件数と代表例を根拠に原則化する。
6. **採否とトレードオフを正直に書く**: 採用した選択、実装から観測できる代替の痕跡（併存する 2 系統・移行途中・非対称）、割り切り（§22）、比較（Appendix A）。**良し悪しを断定せず条件付きで評価する**（B の Appendix A の書き方）。
7. **ナビゲーション**: 本文は他節を `§N` で相互参照する。大きな論点（§21 等）は `####` 小見出しで「方針 → 責務分離 → 論点の確定表 → 経路 → 将来」と分ける。
8. **Appendix が機能する**: A 比較表（観点 × 選択肢）、B 根拠台帳、C 用語表、D 参照、E 優先度付き（P0〜P3）チェックリスト。E は **未確定事項と導入・検証項目の集約先**である。
9. **事実・推定・未確定を書き分ける**（§5 参照）。
10. **文脈のない読み手に通じる**: 固有の略語は Appendix C に定義し、初出で説明する。「前述のとおり」ではなく節番号で参照する。

## 4. 機械検査される床

`validate_design_doc.py` は次を検査する。これは**最低線**であり、B 水準はこれを大きく上回る。検査しない項目（意味の正しさ）はユーザーレビューで確認する。

### 4.4 compact プロファイル

読解対象の可読ファイルが 60 件未満の小規模リポジトリでは自動で `compact`（床を約 40%、台帳 8 件以上など）になる。`--profile standard|compact` で明示もできる。小規模でも**構造（表・図・台帳・調査範囲行）は省略しない**。

## 5. 事実・推定・未確定の書き分け

| 区分 | 書き方 | 根拠 |
| --- | --- | --- |
| 観測 | 断定で書く。数値・名前・パスは台帳の引用と一致させる | `[E<n>]` |
| 推定 | 「〜と読み取れる」「〜を原則としている（N 件中 M 件で一致）」と書く。**件数・代表例・例外**を添える | `[E<n>]` を 1 件以上 + 件数 |
| 採用理由 | README・ADR・コメント等に書かれているものだけを理由として書く。無ければ「意図は文書化されていない」と書き、推定の理由を「推定:」と明示する | `[E<n>]` |
| 未確定 | 実装から判断できない事項（運用手順・組織・本番設定・他リポジトリ）だけを `[要確認]` にする。1 節 2 件まで。残りは Appendix E に優先度付きで集約する | 理由を 1 文で |

観測と推定を混ぜない。**推定を観測として書くことが最大の不誠実**であり、validator の台帳検査はこれを防ぐ最後の砦である。

## 6. 台帳（Appendix B）の書き方

```text
| ID | 証跡 | 引用 | 裏付け |
| --- | --- | --- | --- |
| E1 | evidence: path/to/file#L3-L5 | `ファイルに実在する文字列の一部` | 何を裏付けるか（1 文） |
```

- 引用は**ファイルを開いて**対象行範囲から逐語でコピーする（5〜120 文字、`|` を含めない。空白の連続は同一視される）。
- 行範囲は絞る（原則 10 行以内）。1 つの `E<n>` は 1 つの主張に対応させる。
- 数値・version・名前・環境変数名・ポート・テーブル名は、必ず台帳で裏取りする。
- 本文は `[E3]`、複数なら `[E3][E7]`。台帳に載せたものは必ず本文から参照する（参照されない行は不可）。
- shard note の `## 証跡候補` は `collect_ledger.py collect` が逐語検証して `ledger-candidates.md` にする（ID は安定採番）。本文では `[[path#L行 :: 主張]]` と書けば `collect_ledger.py sync` が実ファイルから逐語引用を作って採番し、**参照された行だけ** Appendix B へ書き出す。

## 7. 提出前の自己レビュー（Selective）

1. 各節を「この節だけを読む人は、何が決まっているか分かるか」で読み直したか。
2. 各 §N の主張は、構造要素（表・図・フロー）で示せているか。段落だけの節は無いか。
3. 数値・名前を台帳で裏取りしたか。推定を観測として書いていないか。
4. `[要確認]` を節末の保険に使っていないか。未確定は Appendix E に優先度付きであるか。
5. §3・§22・Appendix A に、観測できる代替・併存・割り切り（例: 2 系統の生成器、版の食い違い、移行途中）が書かれているか。
6. 層間 import 集計の逆方向・循環を §8 と §22 に反映したか。
7. `validate_design_doc.py` が PASS し、`調査範囲:` 行が導入部にあるか。
