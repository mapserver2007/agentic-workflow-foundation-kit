# 節別プレイブック（B 水準の書き方）

`quality-bar.md` の要件を、節ごとの具体的な作業に落とす。入力は survey の出力（`overview.md`、`facts/*.md`）と shard note の `## 所見` / `## 証跡候補`。**章題は対象実装に合わせて付け替えてよい**（番号・Part・責務は固定）。技術名・章題を B からコピーしない。

## 共通の書き方

- 段落は「主張 → 構造（表・図・フロー）→ 根拠 `[E<n>]`」の順。事実の列挙を段落にしない。
- 他節は `§N` で参照する。固有名詞は Appendix C に定義する。
- 件数は survey の集計（`overview.md` / `facts/imports.md`）から取る。例: 「`app/domain` の internal import は 0 件で外向き依存が無い」「N 件中 M 件が同一規約」。
- 表のセル内に `|` を書かない。fenced code は ` ```text ` を使う。
- `evidence:` 行を本文へ並べない（§9 の備考セルは例外）。

### 構造要素の形の見本（技術非依存）

原則表（§5）:

```text
| 原則 | 要約 | 参照 |
| --- | --- | --- |
| 1. 契約は単一の正本 | <正本の置き場所と変更の起点> [E1] | §2, §10 |
```

責務表（§8）:

```text
| 層 | パッケージ / ディレクトリ | 責務 | やってはいけないこと |
| --- | --- | --- | --- |
| domain | <path> | <責務> [E2] | <観測した禁止事項。例: infrastructure を import しない（逆方向 0 件）> |
```

構成図（§6）:

```text
 利用者 ──▶ ┌────────────┐      ┌────────────┐
            │ <入口 A>   │ ───▶ │ <本体 B>   │ ──▶ [DB] [Cache]
            └────────────┘      └────────────┘
```

ディレクトリツリー（§7）:

```text
repo-root/
├── cmd/            # 実行入口（バイナリごとに 1 ディレクトリ）
└── <dir>/          # <役割>（N files）
```

比較表（Appendix A）: 観点 × 選択肢（◎ ○ △ と 1 行の理由）、末尾に「判断」段落（条件付きで評価する）。

## Part 1 概念編（なぜ）

- **§1 全体方針**: この実装が解く問題と中心の技術方針を、箇条書きで 5〜8 点。続けて「思想の一言要約」を 1 つ書く（B の「核心は X ではなく Y」の形）。入力: README、`overview.md`、entry、compose、docs。
- **§2 契約と正本**: 何が正本か（IDL / schema / 設定 / IaC）、変更の起点、生成物、手編集の可否を表にする（対象 / 正本 / 生成物 / 検証）。入力: `facts/proto.md` `sql.md` `openapi.md` `generate.md`、Makefile の生成 target。
- **§3 採用・非採用方針**: 採用した選択と、**併存・移行途中・版の食い違い**として観測できる代替を表にする（選択 / 観測できる代替 / 評価）。意図が文書化されていなければそう書く。入力: `dep.md` `overview.md`（外部依存の頻度）。
- **§4 技術間の整合**: 主要要素の接続（IDL → 生成 → 実装 → 実行）を fenced の図で示し、接続境界の表（どの版・どの設定が揃うべきか）を添える。入力: compose、Dockerfile、CI、Makefile。
- **§5 設計原則**: 反復して現れる規約を 6〜10 の原則に畳む（原則表）。各原則に観測件数と代表パスを `[E<n>]` で付ける。入力: shard 所見の「反復パターン」、`imports.md`。

## Part 2 アーキテクチャ編（何を）

- **§6 全体アーキテクチャ**: 実行時コンポーネントの構成図、デプロイ単位表（コンポーネント / 実行形態 / ビルド・配備ツール）、コンポーネント間の通信経路。入力: entry、compose、Dockerfile、デプロイ workflow。
- **§7 リポジトリ構成**: 役割コメント付きツリー（`facts/layout.md` を基に 3 階層まで）と、分割の原則（箇条書き）。生成物・テスト・手書きの比率（`overview.md`）を 1 行で添える。
- **§8 レイヤ責務と契約境界**: 責務表（やってはいけないこと列を必ず埋める）。依存方向は `imports.md` から件数で書く。**逆方向 import・循環がある group 対は必ず挙げて §22 にも反映する**。

## Part 3 技術スタック編（具体）

- **§9 技術スタック一覧とバージョン方針**: 4 列表（`レイヤ | 技術 | バージョン方針 | 備考`）を 12 行以上。方針列は `宣言: <値>`（manifest・Dockerfile・CI・install 行の明示 pin）/ `[要確認]`（pin が矛盾・欠落）/ `—`。備考は `観測: <値> [E<n>]`。同じ技術でも成果物が違う pin は行を分ける。入力: `dep.md` `container.md` `tool.md` `ci.md` `make.md`。**§9 内に `---`・`###`・複数の表・`|` を含むセルを置かない**。
- **§10 契約・schema層**: 契約の定義場所、検証者、バージョニング、互換性の扱い。規模（service / rpc / table 数）を `overview.md` から書く。表または図。
- **§11 生成・client層**: 生成パイプラインを表にする（入力 → 生成器 → 出力 → 手編集可否 → 差分検出）。`generated.md` の件数・生成器を使う。
- **§12 利用者向けinterface層**: 公開 interface の runtime・ポート・境界、gateway・middleware。入力: main、compose、routes。
- **§13 service・backend層**: 層構造（§8）の実装形、DI の仕組み、ユースケースの構成（件数）、エラー処理・ログ・トレースの規約、横断関心。shard 所見が主入力。
- **§14 data・storage層**: 保存先ごとの表（用途 / 技術 / schema 管理 / 接続の作り方 / 備考）、migration、キャッシュ。テーブル数と主要テーブル群を `sql.md` から。
- **§15 mock・test層**: テスト種別の表（種別 / 件数 / ランタイム / CI 実行）、mock 生成、fixture、外部依存の差し替え方。`overview.md` の test 件数と外部依存（test のみで使う package）を使う。

## Part 4 開発・運用と横断ルール編（どう動かす）

- **§16 ローカル開発**: 起動までの手順を fenced のフロー（または番号付き）で。依存サービス、環境変数名（値は書かない）、既知の落とし穴。入力: README、compose、Makefile、`env.md`。
- **§17 実装順序**: 変更の種類ごとの順序（契約変更 → 生成 → 実装 → テスト）を番号付きで。生成物の再生成 target と CI の差分検出を結び付ける。
- **§18 CI**: ジョブ表（ジョブ / 契機 / 検査内容 / gate か）、再現性（cache・pin）、**matrix に入っていない実行**・**gate しない設定**など観測できる非対称。入力: `ci.md`。
- **§19 デプロイ・環境分離**: 環境・release の流れ、secret・設定の注入経路（名前のみ）、他リポジトリへ委譲している部分の境界。
- **§20 API・interface設計**: version 表現、error 表現、命名、後方互換の扱い、認可メタデータ。proto / OpenAPI の実例と件数で書く。
- **§21 認証・認可**: **`####` 小見出し 2 件以上**。推奨の流れ: 方針の要点 → 責務分離表 → trust boundary と経路 → token / 署名鍵の取り扱い（名前のみ）→ 将来の拡張・未確定。
- **§22 制約と割り切り**: 版の食い違い・2 系統の併存・移行途中・test を外した範囲など、実装が受容している制約を箇条書き（各項に件数・代表パス・影響）。§8 の逆方向 import を含める。
- **§23 UI・利用フロー**: UI があれば画面・状態・導線・正本。無ければ `該当なし:` に **探した対象**（UI の manifest・ソースツリー・template の有無）を具体的に書く。テンプレート（html/tpl）や API 経由の利用フローがあればここで扱う。

## Part 5 意思決定編

- **§24 結論**: B と同形の fenced 要約（レイヤごとに「採用技術・契約・方針」を 1〜3 行）+ 判断の段落（この実装の立場、割り切り、reverse-draft として確定できないこと）。未確定は Appendix E を参照させる。

## Appendix

- **A 比較**: 観点 × 選択肢の表（観測できる併存・食い違い・代替の評価）。非採用の比較記録が無ければ「記録が無い」と書き、併存の比較に絞る。
- **B 根拠**: 台帳表（`quality-bar.md` §6）。一次情報の URL が README 等にあれば別表で併記してよい。
- **C 用語**: 8 行以上。略語・内部名・生成器名・コマンド名。
- **D 参照**: 8 件以上。リポジトリ内の主要ファイル・ディレクトリを役割別に（`path`: 役割）。
- **E チェックリスト**: 8 行以上、`優先度 | 項目 | 理由` の表。P0 = 設計書の正確性に関わる未確定、P1 = 早期に決める不整合、P2 = 中期、P3 = 長期。本文で `[要確認]` を絞った分はここへ集約する。

## 導出の定石（reverse の勘所）

| 知りたいこと | 見るもの | 書き方 |
| --- | --- | --- |
| 設計原則 | shard 所見の反復パターン、`imports.md` の件数 | 「N 件中 M 件で一致」を原則化し、例外を §22 へ |
| 層の責務 | 各層ディレクトリの card・constructor・interface | 責務表。やってはいけないことは import 集計の 0 件・逆方向件数から |
| 技術の役割 | 外部依存の頻度、import するパッケージ | 「A は B のために使う」。利用ファイル数を添える |
| 版の方針 | manifest の制約、Dockerfile の FROM、CI の matrix、install の pin | 明示のみ `宣言:`。食い違いは行を分け §22 へ |
| 生成の流れ | `//go:generate`、Makefile の生成 target、`generated.md` | 入力 → 生成器 → 出力の表 |
| 環境差 | compose、環境変数名、deploy workflow | 名前のみ。値・secret は書かない |
| 運用の実態 | CI のジョブ・gate 設定 | 「gate する / しない」を区別して書く |
